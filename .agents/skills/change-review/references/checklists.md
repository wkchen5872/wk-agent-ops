# change-review 階段檢查清單

`SKILL.md` 的步驟 5 依 phase 使用其中一份。每一項都要有結果：通過、Finding、不適用（附理由），
或未執行（附原因）。沒有執行的項目不能寫成通過。

## design

審查的是「這份設計能不能被正確實作與驗收」，不是「實作完成了沒」。tasks 未勾、沒有程式都是
design 階段的正常狀態，不能因此判 changes-required 或 blocked。

| 項目 | 檢查什麼 | 典型 Finding |
| --- | --- | --- |
| 需求一致 | proposal 的 Why／What 與 specs 的 requirement 相符，沒有互相矛盾的敘述 | proposal 承諾的行為在 spec 中沒有 requirement |
| 範圍 | 範圍內外明確；沒有夾帶與目標無關的工作 | Non-Goals 寫了但 tasks 仍有對應項目 |
| 介面與依賴 | 外部介面、資料形狀、與其他 Change 或系統的依賴都有說明，依賴的解除條件明確 | 依賴另一個 Change 卻沒寫要等批准、合併或部署 |
| 可行性 | 設計決策在現有程式與工具上做得到；有已知限制時寫明替代方案 | 依賴一個專案沒有安裝、也沒說明如何取得的工具 |
| 風險 | 安全、資料、相容性、回退等重大風險有對應處理 | 資料遷移沒有回退步驟 |
| 測試策略 | 每個 requirement 都有可執行的驗收方式；無法自動化時有可重播的人工步驟 | requirement 只有「應正確運作」，沒有可判定的條件（屬於必要驗證缺口，blocking） |
| 觀察期間與驗收標準 | 需要真實資料的驗收有觀察期間、資料範圍與通過標準 | 「上線後以真實流量驗證」但沒有期間與標準（blocking，請求修正規格） |
| 批准紀錄 | 只檢查紀錄是否符合共用契約；`approved_at` 只有日期是允許的精度 | 批准綁定的版本之後，設計有實質變更 |

結果界線：

- design `pass` 不是人類批准，也不代表任何測試已執行。報告要寫明 Apply 仍需適用的人類批准。
- 批准紀錄無法核對（例如記錄者沒有獨立授權）只代表「不能依這筆代記 Apply」；它不阻止本輪的
  技術審查，也不阻止已獲授權的報告發布。把它寫在回覆的限制說明，必要時列為 Finding。
- 有已安裝的 `openspec-verify-change` 時，不要在 design 階段整套套用它：它把未完成的 tasks 報為
  CRITICAL，那是 implementation 的標準。

## implementation

本 Skill 自帶的基線一定要做；其他 Skill 只是加強。

### 基線（必做）

1. **逐條對照**：每個 requirement 與 scenario，在 reviewed head 中找到實作位置與對應測試；寫下
   對照結果。找不到的就是 Finding 或明確的未完成項目。
2. **tasks 與證據**：已勾的 task 有對應的程式、測試或驗證紀錄；只勾不做是 Finding。
3. **相連程式**：被修改的函式、介面與設定，找出它們的 callers 與使用者（`grep`、型別參照、
   設定引用），檢查是否被影響。
4. **測試**：在 reviewed head 的 checkout 執行專案要求的檢查與受影響的測試，記錄命令、環境與
   結果。無法執行的必要測試寫成未執行並說明缺少什麼。
5. **風險與回歸**：安全（權限、輸入驗證、秘密外洩）、資料、相容性與錯誤處理。
6. **規範**：專案的 `AGENTS.md`、`docs/conventions.md`、`docs/architecture.md` 中與變更相關的規則。

### 加強（有就用）

- `openspec-verify-change`：已安裝時執行，保留它的原始分級，逐項寫明採納或不適用的理由；
  advisory 建議不直接變成強制修改。沒有安裝時寫「未使用，改以基線逐條對照」，不能宣稱調用過。
- `ponytail-review` 或其他品質 Skill：已安裝時可執行；沒有就寫「未執行」。缺少它不構成 blocked，
  也不能拿來省略基線。
- 專案另有明文規定必做的檢查時，那些檢查就是必要的。

### 結論

| verdict | 何時使用 |
| --- | --- |
| `pass` | 選定範圍的基線都有證據通過，沒有 blocking Finding |
| `changes-required` | 有 blocking Finding：已證實的缺陷、安全或資料風險、未達 requirement、必要測試失敗 |
| `blocked` | 必要的檢查或證據無法取得（環境、憑證、真實資料、artifacts 缺漏、版本衝突），或同一爭議沒有新證據 |

- 純風格偏好、可選的微優化、範圍外的功能建議都是非 blocking，可以列出但不影響 verdict。
- 只審了明確指定的子範圍時，可以對該子範圍給 `pass`，同時列出整體 acceptance 中尚未完成的部分。
- 檢查都通過但正式驗收需要等真實資料時，給 `pass` 並分開寫明驗收仍 pending；不宣稱整個 Change
  已驗收，不建議關閉 Issue。

### 複審

- 從上一輪報告的 Findings 與實作者的逐項回覆開始，確認新 head 與修正 commit。
- 每個 Finding 在新 head 上重新驗證，連同受影響的相連行為；只有修正與受影響檢查都有證據才
  Resolved，有理由的反證才 Rejected。實作者的回覆本身不是證據。
- 未變動的輸入可以重用上一輪的結果，但要列出差異範圍作為理由。
- head 只有交付整理（archive 搬移、spec 同步、文件）時，才可以縮小範圍，並附上差異證據；
  有任何語意變動就照完整範圍處理。
