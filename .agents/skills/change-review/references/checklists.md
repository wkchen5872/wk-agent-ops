# change-review 補充檢查

`SKILL.md` 步驟 3 先實際調用必用的 `openspec-verify-change`，再調用適合且已安裝的選用品質
技能（例如 `ponytail-review`、`code-review`），並執行專案要求的測試。這份清單只列這些技能
**沒有涵蓋**、但結論需要的判斷；不重複被調用技能的步驟。每一項都要有結果：通過、Finding、
不適用（附理由），或未執行（附原因）。沒有執行的項目不能寫成通過。

## implementation

預設目的。`openspec-verify-change` 的原始分級照錄，再補上：

| 項目 | 檢查什麼 |
| --- | --- |
| 受測版本 | 測試在 Step 2 選定的版本上執行；有 PR 時是 reviewed head 的 checkout，沒有 PR 時是記錄下來的本機 `HEAD` 與包含的未提交路徑 |
| 必要測試 | 專案要求的檢查都執行並記下命令與結果；不能執行的寫成未執行與缺少的條件 |
| 相連程式 | 被修改的介面或設定，其 callers 是否受影響（選用品質技能沒有涵蓋時才自己檢查） |
| 範圍 | 只判斷選定 Change 與它實際的依賴；PR 中其他 Change 的未完成 tasks 不是 Finding |
| 外部驗收 | 需要真實資料或部署後才能驗收的條件，寫明仍 pending，不算進 pass |
| 本地審查 | 沒有 PR 或查找不明時：開始前已宣告 PR 狀態與報告去向；快照列出 baseline、包含的 staged／unstaged／untracked 路徑、排除範圍與逐檔指紋；結束前重算指紋，內容變動時報告實際檢查的版本 |

## design

只在使用者明確要求設計審查時使用。`openspec-verify-change` 仍然調用，原始分級照錄；
未勾的 tasks、尚未存在的程式屬於實作階段，說明它們不在設計結論的範圍內，不改寫分級，也不
因此判 changes-required。

| 項目 | 檢查什麼 |
| --- | --- |
| 可實作 | 設計決策在現有程式與工具上做得到，已知限制有替代方案 |
| 可驗收 | 每個 requirement 都有可判定的驗收方式；需要真實資料的有觀察期間與通過標準 |
| 依賴 | 依賴其他 Change 或系統時，解除條件明確 |
| 批准紀錄 | 只依共用契約第 9 節判斷：涵蓋實作的使用者指示（當前或可追查的交接）即可，不要求 PR 事件；只有日期的 `approved_at` 是允許的精度，未知的人類識別省略 |

design `pass` 不是人類批准，也不代表任何測試已執行；Apply 仍需涵蓋實作的使用者指示。

## 結論

| verdict | 何時使用 |
| --- | --- |
| `pass` | 選定範圍與版本有足夠證據，沒有 blocking Finding |
| `changes-required` | 已證實的缺陷、安全或資料風險、未達 requirement、必要測試失敗 |
| `blocked` | 必要的檢查或證據無法取得（必用技能缺少、artifacts 不可讀、環境不足、版本衝突），或同一爭議沒有新證據 |

- 純風格偏好、可選的微優化、範圍外的功能建議都是非 blocking，可以列出但不影響 verdict。
- 選用品質技能沒有安裝，不構成 blocked，也不能拿來省略必用的驗證與必要測試。

## 複審

- 從上一輪的 Findings 與實作者的逐項回覆開始，確認新版本與修正 commit。
- 每個 Finding 在新版本上重新驗證，連同受影響的相連行為；只有修正與受影響檢查都有證據才
  Resolved，有理由的反證才 Rejected。實作者的回覆本身不是證據。
- 未變動的輸入可以重用上一輪的結果，但要列出差異範圍作為理由。
