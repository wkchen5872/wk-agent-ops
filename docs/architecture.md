# 🏗️ wk-agent-ops Architecture Guide

> **Project Core Mission**: `wk-agent-ops` is a centralized repository for individuals or teams to develop, manage, and maintain AI Agent enhancements (including Skills, Rules, Workflows, and Git Hooks). The output of this project aims to seamlessly deploy these standardized Agent configurations to other development projects via installation scripts, ensuring consistent, efficient, and highly automated Agent behavior across all projects.

*This file defines the structural integrity of this project. AI agents must respect these boundaries.*

## 1. Core Concept: Template Propagation

wk-agent-ops is a **harness distribution system**. Source templates live in
`template/`, and propagate via `install.sh` to this repo and downstream
projects. Provider-neutral policy lives in managed docs; native rule files are
thin provider entrypoints.

```
template/common/        ← Single source of truth
      ↓
scripts/skills/install.sh
      ↓       ↓       ↓
.claude/ .agents/ docs/  ← This repo's installed tooling and managed policy
      ↓
<target-project>/.claude/ .agents/ docs/  ← Other projects (via --target)
```

**Rule:** Modify `template/`, never `.claude/` or `.agents/` directly.

## 2. Directory Structure & Responsibilities

```

├── template/                  ← Source of truth (edit here)
│   ├── common/                ← Language-agnostic, all projects get this
│   │   ├── .claude/rules/     ← Thin native rules; mirrored to .agents/rules/
│   │   ├── .agents/workflows/ ← Antigravity-native workflow entrypoints
│   │   ├── skills/            ← Shared skills (opsx-commit, doc-updater, etc.)
│   │   ├── AGENTS.md          ← Thin pointer to docs/agent-protocol.md (seed, no-overwrite)
│   │   └── docs/              ← agent-protocol.md/okf-conventions.md (managed) + architecture/conventions starters (seed)
│   ├── python/                ← Python-specific: pytest hook, style guide
│   └── node/                  ← Node-specific: npm test hook
│
├── scripts/
│   ├── skills/install.sh      ← Propagates template/ to .claude/ and target projects
│   ├── workflow/              ← wt-work, wt-done, wt-resume, pm-start (global CLI tools)
│   │   ├── openspec-branch-creator/  ← PostToolUse hook: auto-creates feature branches
│   │   └── entropy-counter/          ← PostToolUse hook: archive-count threshold banner
│   └── notify/telegram/       ← Telegram notification hook setup
│
├── openspec/
│   ├── specs/                 ← Canonical requirements (source of truth for behaviour)
│   └── changes/               ← Active and archived feature changes
│       └── archive/           ← Completed changes (date-prefixed)

├── .claude/                   ← Auto-generated by install.sh (do not edit)
├── .agents/                    ← Auto-generated by install.sh (do not edit)
└── docs/                      ← Managed policy plus project-owned documentation
```

## 3. Workflow Lifecycle Boundaries

PM / RD 是角色分工，不等於固定的 checkout 形式。OpenSpec、Git 與 Provider
session 各自管理獨立 lifecycle；`change-id` 與 `planning_commit` 是 hand-off 的共同
識別資料。

| 階段 | Checkout | 必要結果 |
|---|---|---|
| Explore | 任一安全 checkout；不建立持久化 change | Scope Ready 與唯一 `change-id` |
| Plan | `feature/<change-id>` branch | 已 review 並 commit 的 OpenSpec artifacts |
| Apply | 同一 branch；可為 primary、project-managed 或 provider-native Worktree | 通過 verify 並封存 change |
| Finish | 由已知 cleanup owner 處理 | merge、branch／Worktree cleanup |

Worktree 只在需要同時 checkout 多個工作時使用；單一 Session 可直接在 feature
branch 完成。每個 Worktree 同一時間只能有一個 active writer，跨 Provider 接手
則停止原 Provider，再使用同一個 path。

完整流程見 [PM/RD 多 Agent 協作工作流](/docs/workflow/guide.md)，狀態與 ownership
規則見 [OpenSpec、Git 與 Session 邊界](/docs/workflow/concepts.md)。

## 4. Dependency Rules

- **template/ → install.sh → .claude/ / .agents/ / managed docs** — one direction only; no reverse
- **common/ rules apply to all profiles** — python/node profiles extend, never override common
- **Hook scripts call into notify lib** — `scripts/notify/lib/` contains shared config and registry functions; hooks source these, they do not duplicate logic
- **Workflow core remains provider-neutral** — Claude、Codex、Antigravity 與 Copilot
  的 cwd、session、prompt 差異只存在於 adapters；Gemini CLI 不再是支援目標

## 5. Verification Tools

| Tool | Purpose |
|------|---------|
| `bash scripts/skills/install.sh` | Verify template propagation works (use a temp git repo) |
| `/opsx:verify` (Claude Code) | Verify change implementation against specs |
| `/openspec-verify-change` (all tools) | Same, multi-tool compatible |
| `diff template/common/.claude/rules/... .claude/rules/...` | Confirm Claude rules match source |
| `diff template/common/.claude/rules/... .agents/rules/...` | Confirm Antigravity mirrors the same native entrypoint |
| `diff template/common/docs/agent-protocol.md docs/agent-protocol.md` | Confirm managed policy matches source |
