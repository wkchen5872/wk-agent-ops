# 🏗️ wk-agent-ops Architecture Guide

> **Project Core Mission**: `wk-agent-ops` is a centralized repository for individuals or teams to develop, manage, and maintain AI Agent enhancements (including Skills, Rules, Workflows, and Git Hooks). The output of this project aims to seamlessly deploy these standardized Agent configurations to other development projects via installation scripts, ensuring consistent, efficient, and highly automated Agent behavior across all projects.

*This file defines the structural integrity of this project. AI agents must respect these boundaries.*

## 1. Core Concept: Template Propagation

wk-agent-ops is a **harness distribution system**. Source templates live in
`template/`, and propagate via `install.sh` to this repo and downstream
projects. Provider-neutral policy lives in managed docs; native rule files are
thin provider entrypoints.

```
template/common/        ← Single source of truth
      ↓
scripts/skills/install.sh
      ↓       ↓       ↓       ↓
.claude/ .agents/ .codex/agents/ docs/ work-items/  ← Installed tooling and managed policy
      ↓
<target-project>/.claude/ .agents/ .codex/agents/ docs/ work-items/  ← Other projects

selected language profile
      ↓
scripts/skills/install.sh → npx skills add testland/qa
                              ↓
                    project-local runner + triage
```

**Rule:** Modify `template/`, never `.claude/`, `.agents/`, or managed
`.codex/agents/` files directly.

Mutation testing intentionally uses a second distribution lane: wk-agent-ops
selects the language mapping and retains TDD/score/safety policy, while the
skills CLI installs testland/qa runner and triage skills project-locally. Those
third-party skills are not copied into `template/common/skills/`.

## 3. Workflow Lifecycle Boundaries

PM / RD 是角色分工，不等於固定的 checkout 形式。OpenSpec、Git 與 Provider
session 各自管理獨立 lifecycle；`change-id` 與 `planning_commit` 是 hand-off 的共同
識別資料。

| 階段 | Checkout | 必要結果 |
|---|---|---|
| Explore | 任一安全 checkout；不建立持久化 change | Scope Ready 與唯一 `change-id` |
| Plan | `feature/<change-id>` branch | 已 review 並 commit 的 OpenSpec artifacts |
| Apply / Review | 同一 branch；可為 primary、project-managed 或 provider-native Worktree | 實作與驗證；Review 綁定受審版本，可停在未封存、未提交 |
| Finish | 原工作 checkout | 依授權 archive → docs → commit；預設本地完成，PR 交付另依授權 |
| Git 整合與清理 | 由已知 merge／cleanup owner 處理 | 另行授權的 merge、branch／Worktree cleanup |

實作、封存、提交、遠端交付、合併與部署各有自己的完成證據；一個階段完成不代表下一個
已完成。交付擴充設計的成功交付只到最終 head 的 Review 與 Closure，merge 與 Issue
結案分開處理。[^delivery-policy][^commit-workflow]

Worktree 只在需要同時 checkout 多個工作時使用；單一 Session 可直接在 feature
branch 完成。每個 Worktree 同一時間只能有一個 active writer，跨 Provider 接手
則停止原 Provider，再使用同一個 path。

完整流程見 [PM/RD 多 Agent 協作工作流](/docs/workflow/guide.md)，狀態與 ownership
規則見 [OpenSpec、Git 與 Session 邊界](/docs/workflow/concepts.md)。
本 repo 採用的 [本機四階段流程](workflow/local-development.md) 與
[正式圖稿索引](diagrams/README.md) 提供各階段與團隊 GitHub 交接的圖文入口。

## 4. Dependency Rules

- **template/ → install.sh → .claude/ / .agents/ / .codex/agents/ / managed docs / `work-items/AGENTS.md`** — one direction only; no reverse; other `.codex/` content remains external
- **Managed convention ≠ collaboration records** — the installer refreshes only
  `work-items/AGENTS.md`; it never creates, changes, or removes local `work-items/WI-*/` records
- **GitHub handoff has one contract** — `docs/github-handoff.md` owns the Issue, PR,
  review, Checkpoint, and Closure formats (Handoff → content → Next actions → Author) and
  the write-time checks (full repository target, operation, authorization, readback); the
  `github-issue`, `github-pr`, and `change-review` skills and the thin rule only reference
  it. Issue close and PR close each change only their selected target. GitHub calls use an available gh or GitHub MCP. Only `github-pr create`
  commits and pushes — scoped to its own work, without force or hook bypass; every other
  operation leaves Git alone. Git owns commit, push, and authentication; there is no custom
  identity script. No hook enforces this
- **common/ rules apply to all profiles** — language profiles extend, never override common
- **language profile → testland/qa runner + common triage** — installer selects
  one runner per profile and one deduplicated `mutant-survival-triage`; no
  third-party mutation SKILL.md is vendored in the template
- **Hook scripts call into notify lib** — `scripts/notify/lib/` contains shared config and registry functions; hooks source these, they do not duplicate logic
- **Workflow core remains provider-neutral** — Claude、Codex、Antigravity 與 Copilot
  的 cwd、session、prompt 差異只存在於 adapters；Gemini CLI 不再是支援目標

## 5. Verification Tools

| Tool | Purpose |
|------|---------|
| `bash scripts/skills/install.sh` | Verify template propagation works (use a temp git repo) |
| `/opsx:verify` (Claude Code) | Verify change implementation against specs |
| `/openspec-verify-change` (all tools) | Same, multi-tool compatible |
| `diff template/common/.claude/rules/... .claude/rules/...` | Confirm Claude rules match source |
| `diff template/common/.claude/rules/... .agents/rules/...` | Confirm Antigravity mirrors the same native entrypoint |
| `diff template/common/.codex/agents/... .codex/agents/...` | Confirm Codex custom agents match their templates |
| `diff template/common/docs/agent-protocol.md docs/agent-protocol.md` | Confirm managed policy matches source |
| `diff template/common/work-items/AGENTS.md work-items/AGENTS.md` | Confirm the managed Work Item convention matches its source |
| `bash tests/test_github_handoff.sh` | Contract presence and managed delivery of the GitHub handoff assets |
